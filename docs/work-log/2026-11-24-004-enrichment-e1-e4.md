## Changes and findings so far

- **Encoder over the whole corpus** (GLiNER-Relex, GPU, 83.5 ms per paper, 13,617 papers, 19 min); outputs
  identical to the CPU run on the 100 development papers (`data/interim/enrichment-v1/mentions-relex.jsonl`,
  ignored). `ops/extract/run_encoders.py` is now resumable and flushes per chunk.
- **SLM verification and relation generation over the whole corpus** (Qwen3.5-4B Q4_K_M, config frozen from
  K1): about 0.4 papers per second because the laptop GPU runs at about 1.1 GHz under its power cap, so the
  run takes roughly 9 hours. Resumable by paper. A compact text format for relations halved completion
  tokens but dropped dev relation F1 from 0.400 to 0.325, so it was not used (`verify-text` mode kept as a
  documented variant). `llama-server` raised to 4 slots (`LLM_PARALLEL=4`), a runtime setting.
- **Code**: `enrich/entities.py` (mentions with dropped spans and reasons, surface merge, node threshold),
  `finalize.py` (QID merge), `link.py` (Wikipedia search, MiniLM scoring, guards), `relations.py` (all seven
  predicates), `graph5.py` (build, validator, counts), `load5.py` (port 7690 only), `e2.py`/`e3.py`
  orchestration, `quality.py` (E4 freeze, packets, scoring), `ops/extract/embed.py`.
- **Dev decisions recorded** (`reports/enrichment-v1/link-dev.json`, `merge-dev.json`): the Wikipedia link rule
  (score at least 0.40, name must occur in the page title or lead, disambiguation and list pages excluded,
  name must match the title) accepted 8 of 120 development entities, 7 correct and 1 broader, 0 wrong; most
  specific method names have no Wikipedia page, so linking recall is low by design. Embedding-based surface
  merging never reached 90% precision on a 70-pair sample (about half at cosine 0.90 or more), so its
  threshold is 0.97 (effectively off); duplicates are handled by lemmatized keys, acronym expansion and the
  shared-QID merge.
- **Rehearsal on the first 900 papers** (ignored `data/interim/enrichment-v1-rehearsal/`): extract, link, build,
  validate (v4 layer through the frozen v4 validator, 0 errors; enrichment rules, 0 errors), and load into a
  new `neo4j-enriched` service on bolt 7690; a load to 7689 is refused. Inventory and integrity queries
  (`queries/enriched-*.cypher`) returned the expected counts and zero violations. Rehearsal counts are not results.
- **Spec deviations to record**: relations are generated from the whole abstract, not per sentence (only about a
  fifth of paper-level relations have both endpoints in one sentence; `same_sentence_papers` is stored per edge);
  the Wikipedia lead texts and abstracts stay in ignored local stores.

## Update 2026-11-24 23:45 +07:00 (full-corpus run, E2, review fixes)

- **SLM run** finished 20:56 for all 13,617 papers (21,098 s of resumed wall time, 17.1M prompt and 1.18M
  completion tokens), 0 invalid papers. The `llama-server` died once at 15:03 with a CUDA "unknown error" (segfault,
  GPU fault); a supervisor script restarted the server and the resumable run. The laptop GPU ran between about 1.0 and
  2.4 GHz under its power cap, so throughput varied from 0.17 to 1.1 papers per second.
- **Retries and truncation**: the call log (which spans the crashed segment too) shows 53 calls that needed a retry and
  36 calls that stopped on `finish_reason: length`; all 36 are relation-generation calls (`max_tokens` 400), about 18 papers
  with two attempts each. The client retries once and the relation step then returns no relations for that paper, so
  those papers keep their entities but have no SLM relations. Entity verification never hit the limit; 15 mentions got
  `no_decision` (the model skipped them) and are recorded as dropped.
- **SLM-only ablation variant** run on the 200 test papers (extract prompt, 1,395 s, 200 valid).
- **E2 counts** (`reports/enrichment-v1/entities.json`): 141,889 candidate mentions, 63,892 kept, 77,997 dropped with reasons;
  2,012 entity nodes at 3 or more papers (Method 957, Task 683, Dataset 372) after `entity_key`; encoder-only baseline 3,167 nodes.
- **Normalization refinement after the full-corpus run**: `entities.entity_key` (strip a trailing parenthetical acronym, split letters from
  digits) was added after looking at the most frequent node names across the whole corpus (aggregate lists, not item-level test
  output); the node count moved from 2,003 to 2,012. A reviewer then found that `textutil._stem` turned "processes" into "processe";
  `_stem` now handles -ies and -es plurals, keeps -ss/-us/-is and a small exception list, and the acronym pattern accepts a leading digit
  ("3D Gaussian Splatting (3DGS)"). Dev scores are unchanged to four decimals (entity F1 0.6701, relation F1 0.4000). No item-level
  output of a test paper was inspected for these fixes; the aggregate node lists they came from include test-paper mentions, so the
  claim is that no test-paper-specific error drove them, not that test papers were untouched.
- **Rehearsal caveat**: the 900-paper rehearsal (AAAI 2021) probably included some test papers; it only checked build, validate and load. No
  threshold or prompt changed after it.
- **Linking**: Wikipedia answers 429 after about two requests in a row, so the run is throttled to about one search per six seconds
  (about 2,000 searches); it was at 1,622 at 23:43.
- **Spec deviations** (also in the D042 amendment): verification runs per paper, not per sentence, and APPLIED_TO and EVALUATED_ON
  are generated from the whole abstract. Only 5,064 of 30,251 paper-level relations have both endpoints in one sentence.
